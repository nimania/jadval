# معماری توسعهٔ «پیام جدول» — چندنوعی، قالب‌محور و بانک مشترک
تاریخ: ۱۴۰۵/۰۸/۱۲

## هدف محصول
«پیام جدول» برند و پلتفرم انواع سرگرمی فارسی است. «جدول کلمات متقاطع» فقط یک **نوع بازی** است و باید با نام کامل در ناوبری، آرشیو و فراداده معرفی شود. هیچ دادهٔ خصوصی یا سرنخ‌های بانک به‌صورت دسته‌جمعی در مخزن GitHub Pages نباید قرار بگیرد.

## ۱. معماری نوع بازی و آرشیو
- کلید پایدار نوع بازی: `crossword`. عنوان فارسی نمایشی: «جدول کلمات متقاطع».
- بازی‌های آینده ممکن است «جدول واژه‌یابی»، «جدول سودوکو»، «حدس کلمه»، «معمای تصویری» و موارد دیگر باشند؛ این‌ها **فعلاً محصول منتشرشده نیستند**.
- آرشیو هر نوع بازی در مسیر `/?type=<gameType>` با دسته‌بندی جداگانه و شناسهٔ ثابت هر بازی.
- پیوندهای قبلی `/?id=pub_...` همیشه باید حفظ شوند.
- ساختار منتشرشدهٔ فعلی `publishedPuzzles` مخصوص جدول کلمات متقاطع است. ثبت انواع بازی‌های جدید باید در collection جدا یا با مدل نسخه‌دارِ مناسب و قواعد امنیتی جدا انجام شود؛ نباید شکل اسناد قبلی را شکست.
- قالب شناسهٔ داده‌ای پیشنهادی برای محتوای جدید: `{type,id,title,status,createdAt,publishedAt,templateId,payloadVersion,payload}`. برای مهاجرت دادهٔ قدیمی، `type=crossword` خوانده شود و هرگز فایل قدیمی بازنویسی اجباری نشود.

## ۲. کارگاه ساخت برای همکاران
- مسیر ساده: «انتخاب نوع و قالب» → «ساخت پیش‌نویس» → «بررسی سؤال‌وجواب، کیفیت و پیش‌نمایش» → «درخواست تأیید/انتشار».
- امکانات تخصصی/بانک/امنیت در حالت پیشرفته باقی بمانند.
- حقوق دسترسی جدا: `owner` (تنظیم امنیت، بانک، انتشار)، `editor` (ساخت و پیشنهاد)، `reviewer` (تأیید)، `publisher` (انتشار). **قواعد فعلی فقط حساب‌های در admins با enabled=true را می‌شناسند؛ نقش‌های ریزتر هنوز پیاده‌سازی نشده‌اند.** دادن همان مجوز مدیر به همکار راه امنِ جایگزین نیست.
- گردش کار نسخه‌دار: `draft → in_review → approved → published`. تغییر پس از تأیید باید تأیید تازه بخواهد.
- هر تغییر در بانک یا جدول: نویسنده، تاریخ، نسخه، نتیجهٔ کنترل تعارض و تاریخچهٔ ویرایش.
- قبل از ورود همکار دیگر، احراز هویت و امکان بازیابی بانک از سرور باید کامل و آزمایش شود.

## ۳. موتور قالب‌ها
- قالب هندسی ذخیره‌شده: `{id,gameType:'crossword',size,mask,displayName,source,version,status}`.
- جهت فیزیکی آرایهٔ ماسک: ردیف‌ها بالا به پایین، ستون‌ها در آرایه چپ به راست؛ نمایش جدول فارسی و افقی راست به چپ. این تصمیم باید در import هر قالب کنترل شود.
- هنگام دریافت طرح جدید از تصویر: استخراج شبکه به ۱۵×۱۵، بازبینی مختصات دستی، بررسی تعداد خانه‌های سیاه/تقارن/پیوستگی/طول جایگاه‌ها، ثبت نسخه و پیش‌نمایش. تصویر فقط **ورودی بررسی** است و به‌تنهایی نشانهٔ درستی دیجیتال‌سازی نیست.
- هنگام انتخاب یک `templateId` باید **همان قالب** به حل‌گر داده شود. در حالت `auto` موتور اجازه دارد میان طرح‌های مختلف جست‌وجو کند.
- اگر قالب ثابت با بانک حل نشد، گزارش بده؛ بدون اطلاع طراح به قالب دیگری تغییر نده.

## ۴. فرهنگ‌نامهٔ مشترک همهٔ بازی‌ها
موجودیت‌های منطقی مستقل را تفکیک کنیم:
1. `lexemes/{wordId}`: صورت معیار کلمه، شیوهٔ نرمال‌سازی، شکل نمایشی، تعداد حروف، ریشه/گونه‌های نوشتاری، حوزه و وضعیت.
2. `clues/{clueId}`: متن سؤال، زبان، شناسهٔ پاسخ/پاسخ‌ها، نوع سرنخ، دشواری، منبع، حق استفاده و تاریخچهٔ اصلاح.
3. `gameUsage/{usageId}`: ارجاع به واژه و سرنخ در بازی منتشرشده و آمار استفاده/تکرار.
4. `submissions/{submissionId}`: پیشنهادهای پیشنویس از چت/وب/همکاران؛ هیچ رکوردی بدون بررسی و تأیید به بانک رسمی اضافه نشود.
5. `templates/{templateId}`: الگوهای نسخه‌دار، مستقل از بانک واژه.

**مهاجرت:** فعلاً collection فعلی `entries` را بدون تغییر نگه داریم؛ ابتدا لایهٔ API و نمای سازگار برای واژه/سرنخ بسازیم. پس از گرفتن نسخهٔ پشتیبان و بررسی کامل صحت داده، مهاجرتِ کپی‌شونده و برگشت‌پذیر انجام دهیم. عدد ۱۹٬۸۰۴ مدخل فعلی نباید از دست برود.

## ۵. افزودن از همین گفت‌وگو
- کاربر می‌تواند دسته‌ای «پاسخ | سؤال | موضوع | منبع» در گفتگو بدهد.
- دستیار آن‌ها را نرمال و تکراری‌های احتمالی را مشخص کند و **پیشنهاد** قابل بررسی ارائه دهد.
- با تأیید صریح کاربر، محتوای آمادهٔ import خصوصی ساخته شود یا از اتصال مجاز و دارای نقش نویسنده برای افزودن استفاده شود.
- هرگز واژه‌های خصوصی بانک را برای جست‌وجو یا نمایش در GitHub عمومی کپی نکنیم.
- اگر دسترسی مستقیم به Firestore در گفتگو موجود نباشد، نباید ادعای ثبت مستقیم کنیم. روش جایگزین: خروجی TSV/JSON و پیش‌نمایش‌دار در کارگاه.

## ۶. اولویت اجرا
۱) پایدارسازی آرشیو نوعی و پیوندهای قبلی؛ ۲) پنل سادهٔ ساخت و انتخاب قالبِ واقعی؛ ۳) ارسال پیشنهاد واژهٔ گروهی به صف بررسی، با مقایسه با بانک؛ ۴) API بانک مشترک، تأیید و نقش‌های امن؛ ۵) افزودن نخستین نوع سرگرمی دیگر.

## آزمون‌های الزامی
- لینک‌های قدیمی گم نشوند؛ نوع `crossword` همچنان قابل بازی باشد.
- هر پاسخ صحیح، از شبکه و سرنخ همان جدول بیاید.
- الگوی انتخابی تغییر پنهانی نکند؛ خطا قابل توضیح باشد.
- درج تکراری با نرمال‌سازی ی/ک و فاصله شناسایی شود.
- کاربر بدون مجوز هرگز بتواند `entries` یا `submissions` خصوصی را بخواند/بنویسد.
- قبل از هر import گروهی، پیش‌نمایش شمار مدخل، برخوردها، نسخهٔ پشتیبان و تأیید نهایی.
